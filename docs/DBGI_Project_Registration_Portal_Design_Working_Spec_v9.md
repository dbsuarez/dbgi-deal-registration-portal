# DBGI Project Registration Portal - Working Design Specification v9

**Status:** Working design record, not yet the final Claude Code build handoff.  
**Version:** v9, superseding v8.  
**Prepared:** 2026-09-29.  
**Updated:** 2026-10-17, incorporating registration-form and initial stack/hosting decisions below.  
**Version note:** This is the current specification; earlier generated v1-v8 documents are superseded, not physically deleted from the conversation file panel. This document incorporates the ranking decision made after v8.

## 1. Purpose and deployment

- Build a standalone, cloud-hosted DBGI project registration portal at `registration.dbgi.ph`; the existing `dbgi.ph` website links to it. The portal uses **its own database** for products, product prices, companies, users, projects, registrations, rankings, approved discounts, reorders, settings, notifications and audit logs. It does not depend on Odoo for authentication, products, price calculations or orders.
- **Initial implementation and deployment stack decision:** use Django for the quickest end-to-end delivery, with Django templates and progressive enhancement rather than a separate frontend initially. Deploy with Docker on a Hostinger VPS. Use PostgreSQL as the application database and keep it on a private Docker network, with persistent storage and tested backups. Configure the VPS reverse proxy and TLS for `registration.dbgi.ph`; keep secrets outside the image/repository. The existing Hostinger Business web-hosting plan is not the application runtime for this Docker deployment. Add private object storage and background workers only when required by the implemented attachment/notification needs; do not expose database or internal service ports publicly.
- Company/dealer users register particular government procurement opportunities. DBGI groups registrations that actually describe the same procurement/lot, assesses advance evidence, confirms company-level rank and approves project/item discounts. This is a DBGI commercial deal-registration process, not a government award or bidder ranking.
- Build a responsive web application backed by authenticated server operations. Browser-only storage, hard-coded company/product data and prototype placeholder features are not acceptable production architecture.

## 2. Roles and authorization

- **DBGI admin:** creates/manages companies and company users; manages catalog/prices/settings; reviews evidence, project matching, company edits and rankings; approves item discounts and renewals; verifies reorders and approves documented corrections/reversals; resolves withdrawals, exceptions and disputes; sees full authorized audit/ranking/report data.
- **Company user:** employee of an admin-managed company. Can submit and edit that company's project registrations; see its own company projects, confirmed rank, approved price terms and notices; record and edit pending reorders; withdraw a pending reorder with a reason; request renewal, exception review or a correction of a verified reorder. Cannot see other companies' data/full rankings or edit authoritative prices, approvals or verified records.
- Multiple users in one company count as **one company** for an opportunity's ranking. Duplicate employee submissions must not yield another queue place. Server-side company scoping is mandatory for each API, page, file, notification and export.
- **Any DBGI admin** may verify an ordinary reorder and approve a documented correction or reversal. Record the admin identity, timestamp, reason and change. A separate pricing approver role is not required initially; adding one later is an optional organizational change, not an assumed v9 permission requirement.

## 3. Opportunity, evidence and ranking

- Model an internal **specific project/opportunity** separately from each company's **registration**; a registration can contain multiple hardware/consumable item lines. Procurement lots may require distinct ranking scopes.
- Generate server timestamps and immutable original submission/evidence snapshots. An advance claim may lack a PhilGEPS reference, but must initially identify a specific agency purchase; vague speculative opportunities cannot later inherit an earlier rank from supplemental detail.
- Require an evidence description and authorized-sharing attestation; optionally allow an appropriate public link or private attachment. Warn against unreleased/confidential bids, unnecessary personal information, IDs/signatures, other companies' proposals or pricing. DBGI reviews specificity and credibility and records decisions. A later PhilGEPS notice can be proposed by a company or attached by DBGI, but only DBGI confirms same-project/partial-lot/different-project matching, documenting agency, office, purpose, items, timing, location and scope. A validated match retains an otherwise eligible original time.
- Admin reviews competing claims, material edits and notice/lot matching before confirming rank. Company users see only their own confirmed rank, never provisional rank/full rankings or competitors' details. Discount approval is a separate admin step after ranking.
- **Before ranking companies, the system must determine whether their registrations concern the same specific procurement opportunity or lot.** It may automatically match only when exactly one existing scope has identical normalized end-user and address values, complete requested-product overlap, and no conflicts. Use DBGI review for every ambiguous, partial, or conflicting result, including reasonable naming variations, incomplete product overlap, or evidence that may indicate separate purchases or lots.
- **Only after DBGI confirms that registrations compete in the same opportunity/lot ranking scope, rank the participating companies by their original eligible, server-recorded submission timestamps.** DBGI review or approval time, user-entered dates and later edits cannot replace the original timestamp. An early submission that was too vague to identify a specific procurement cannot later gain earlier priority from supplemental details. Record DBGI's matching decision and rationale.
- Advance-registration expiry, reminder lead time and clarification periods have explained admin settings. A clarification hold preserves an original time only if the original was sufficiently specific; vague originals gain no hold. An admin-approved extension before advance expiry can preserve eligible time; expiration/rejection removes a claim from the active queue. An advance claim's priority expiry is distinct from an approved discount's expiry.
- Admin controls project merge/split with reason and reviews resulting rank/discount changes. Company users request withdrawal; DBGI confirms before removing a project registration from its active ranking queue.

## 4. Registration form and catalog

- The initial company-user form starts with the partner/company account prefilled from the DBGI-managed account; end-user name, complete address, project opportunity title, bid date, delivery date, contact person, designation, email and contact number. Keep this as the starting field set; additional fields can be added later. Do not copy Canon's `New` status label as DBGI policy; use DBGI-specific statuses and review states.
- Use a **single common registration form** with repeatable item rows and conditional category-specific fields. Organize company/submitter, procuring agency/end-user, specific purchase description, stage and external/internal references, evidence, timetable and product lines. Don't require an unavailable PhilGEPS reference or exact final model for a valid advance claim.
- Require at least one competitor-item row per registration, with competitor brand, competitor item/model, competitor bid price and remarks. Treat competitor information as sensitive: scope access to the submitting company's authorized users and DBGI admins, do not expose it to other companies, and do not include it in email notifications.
- Use a searchable product picker that supports multi-selection and shows product code, name and category. Show SRP only where the existing company price-visibility rules permit it; otherwise omit the price while keeping the catalog selection usable. DBGI admins maintain portal-native products, categories and product prices. Allow `Not in catalog` as a requested item pending review.
- Each selected item can include quantity, a requested unit price and remarks/justification. A requested price is the company's proposal for DBGI review, not an approved discount or final price. Keep approval and monetary calculations server-side; show the request distinctly from any approved terms. Apply the existing price-visibility rules to SRP and other price data.
- Include an evidence description and authorized-sharing attestation, with an optional public link or private attachment. Warn against unreleased/confidential bids, unnecessary personal information, IDs/signatures, other companies' proposals or pricing. Secure private attachments with authorized access.
- Initial prototype attachment defaults (not yet DBGI policy): maximum 10 MiB per file; PDF, PNG/JPG/JPEG, DOCX and XLSX extensions; random storage names in private media storage; authenticated downloads scoped to the registration's company or DBGI admins. Files are not served directly from the media volume. Confirm permitted formats, file-content scanning, retention/deletion and operational backup requirements before production.
- The exact conditional/required field matrix for advance versus published registrations, category-specific fields and project status transitions still needs sign-off.
- Public DBGI website product examples inspected 2026-10-17 (reference only; not a verified or complete administrative catalog, and no prices inferred):
  - Scanning: ES221 one-dimensional laser barcode scanner; E14952 handheld barcode scanner.
  - Safe boxes: ET531, ET533, ET540, ET541, ET552 digital safes; ET585 fireproof hotel safe; ET590 and ET591 fingerprint safes.
  - Laser printers: M1820W and P1820W 20 ppm monochrome laser printers.
  - Thermal label printers: E760DW 3-inch/80 mm thermal label printer; ES340 4-inch thermal label printer.
  - Other listed products: ES001 Deli red laser pointer; T108 laser printer toner cartridge (for P1820W and M1820W).
- Initial catalog seed decision (2026-10-17): seed only M1820W and P1820W as active `Laser Printers` catalog products, each named `20 ppm monochrome laser printer`, with no prices. These two models were selected by the user from the public product examples for the initial portal catalog; all other examples remain reference-only until DBGI approves adding them.
- The Epson workbook `FY26-Epson-Tender-Form-1-A_1.xlsx` is form-section inspiration only. Its manufacturer's opportunity-ID mandate, response times, specific model catalog and 60-day tender rule are **not** DBGI policy. The uploaded `mamahaling_enterprise_system.html` is UI inspiration for cards, role-appropriate tables, repeatable rows, badges and reports, not a usable database/security design.

## 5. Product price management

- A DBGI admin can create a price change that **takes effect immediately** or is **scheduled for a future effective date/time**. Show scheduled changes to authorized admins. Keep dated/versioned price history; changes never overwrite a prior verified order snapshot.
- Each product's maintained price has a **configurable VAT basis**, defaulting to **VAT-inclusive**. Admin may set VAT-exclusive for a particular product. Display the selected basis alongside the price; changing it applies to new applicable calculations and does not rewrite historical snapshots. The exact VAT breakdown/tax compliance treatment still needs pricing/finance sign-off.
- Company users can see the applicable current price and discount calculation **only for products covered by their own approved project or reorder**. DBGI admins can see and manage the full price catalog. Apply the same scope to API responses and exports.
- A reorder uses the portal's DBGI-maintained **price version effective on the verified order date**, not merely the price current when the user fills out the form. A company-entered date must not automatically select an older price when late or disputed: flag for DBGI review, preserve claimed order date, server-entry time, price version, evidence and admin decision. DBGI verifies the date before finalizing the order price.
- At initial discount approval, show eligible product, applicable current unit price, discount percentage or flat peso amount per unit, per-unit savings, resulting discounted unit price, savings for entered quantity, expiry date and `Subject to availability`. Identify a displayed price as **current**, not a guaranteed unchanged base price for future reorders. Company users see **no discount figures before DBGI approves** the discount.

## 6. Discount approval and calculation

- DBGI admins set discount terms separately for each project/company and eligible item, taking rank into account. There is no universal mandatory percentage schedule. Explained admin defaults may prefill an approval, but only explicit project/item approval creates a benefit. Discount may be a **percentage** or a **flat peso amount per unit**. Record applicable company, end-user, approved product/model, purchase context, item terms, start/end validity and any conditions.
- On each eligible transaction, use the applicable DBGI-controlled unit price and approved discount version. Show per-unit discount, resulting discounted unit price, quantity and line savings. For percentage discounts, **calculate with full precision and round each item-line discount total to two decimal places**; display a readable two-decimal per-unit discount, but do not derive line totals by multiplying the displayed rounded figure. Preserve the underlying calculation and price version to explain any centavo display differences. Define the exact currency rounding mode, VAT interaction and monetary library before build.
- **No automatic stacking** of a project discount with another DBGI discount on the same product. Any intentional combination requires explicit admin approval for that particular purchase, with documented terms, calculation and reason.
- Approved terms or rate changes require admin before/after audit entries, reason, approver/time and company notification. Company edits of material project/item details trigger `Edited` and `Review required`, rather than silently changing a confirmed approval.
- Initial approved-discount validity is an **admin-configurable default**, with an admin override for each approval; the actual duration has not yet been selected. Preserve each approval's concrete dates. Changing defaults does not rewrite existing approvals.

## 7. Repeat reorder entitlement and verification

- An active approved discount can cover **multiple qualifying reorders** of the approved product by the **approved company** for the **same end-user**, with **no aggregate quantity/value limit until its expiry**, while supplies last. No fresh discount approval is needed per ordinarily qualifying reorder. This is not a stock reservation or guarantee of fulfillment; absent an inventory integration, show `Subject to availability` and no invented stock number.
- A **new procurement notice alone does not cancel an existing active discount**: a covered same-end-user/product purchase can still receive its existing discount, even where the later notice must be registered/ranked as a distinct opportunity. The prior rank does not automatically transfer to the new project's queue. Do not automatically treat a different product/end-user as covered.
- Company users can record their company's reorders in the portal. Preserve server-recorded entry time and user-claimed order date, product/model, end-user, quantity, purchase reference if available, and notes/attachments if appropriate. **Proof of order (reference/document) is not mandatory for an ordinary reorder**, but DBGI can require it when it flags an exception. A company entry is a claim, not proof that stock was supplied or the purchase verified.
- For an ordinary entry matching an active approval, immediately show a calculated price **provisionally**, labeled `Based on your recorded reorder-subject to DBGI verification and stock availability`. No calculation is final until DBGI verifies the reorder. Late or mismatched cases do not show an old discount as confirmed.
- **Every reorder requires DBGI verification** before the price and discount become final, not only exceptions. DBGI checks claimed/actual order date as warranted, same company/end-user/product and approved context, eligibility at that date, applicable effective price and supply availability as part of its actual sales/inventory process.
- Once verified, **lock the reorder** and snapshot the verified order date, relevant product and VAT/price version, approved discount version, unit price, per-unit discount, line-total savings and resulting discounted unit price/total. Later price/discount updates affect later transactions, not the verified snapshot.
- Before verification, company users can **edit** a pending reorder (audit each version) or **withdraw it with a reason** (retain history). After verification, a company cannot directly edit/withdraw; it may request a correction. Any DBGI admin can issue a reasoned documented **correction or reversal**, preserving the original verified snapshot and notifying the company via the existing per-event notification configuration.

## 8. Reorder exceptions and clarification

- If a company enters a reorder **after its discount has expired**, do not apply its old discount automatically, even if the user claims a pre-expiry purchase date. Mark `Late reorder-DBGI review required`, alert DBGI and retain claimed date and server-entry timestamp. DBGI requests a purchase reference/supporting evidence and may explicitly approve a verified genuinely pre-expiry order or reject it with evidence and reason. This one-order exception is not a backdated renewal or general discount extension.
- If company/end-user/product/purchase scope or terms do not match the approved discount, show `Requires DBGI review`, send the admin an alert and do not apply old terms automatically. DBGI can correct an evident entry error or make an explicit decision on a changed-scope request, with recorded justification and company notice.
- **Give the company a chance to explain** a flagged exception. DBGI can request specific clarification/evidence, set a response deadline and leave the reorder pending without a final discount. The deadline uses an **admin-configurable default** and permits a per-case override with a logged reason. Preserve request, response, deadline and decision.
- If no response comes by the deadline, move the case to an **overdue admin queue**; do **not** auto-reject or silently approve it. A DBGI admin makes and records the final outcome. Ordinary reorders still require verification; exception cases are higher-priority review items.
- A possible duplicate reorder must be **flagged and shown to the company and DBGI for review**. The portal must not automatically merge or reject it. If DBGI confirms that it is a duplicate, mark it **`Duplicate-closed`**, link it to the original reorder, preserve the duplicate's audit history and exclude it from separate reorder and discount counts. A duplicate check should consider the company, end-user, purchase reference, product lines, quantities and relevant purchase context; identical company/end-user details alone are not enough to prove duplication.
- One reorder may contain **multiple product lines under the same purchase/order reference**. If only one line does not match the approved registration or discount, DBGI can process the matching lines while holding the unmatched line for review. Notify the company which line is awaiting approval. If DBGI rejects the unmatched line, the other lines remain processed and only that line is marked rejected with the rejection reason recorded and shown.
- A company may withdraw one pending product line without withdrawing the entire reorder, provided it gives a reason; record the withdrawal in the audit history. If a company edits a pending line, restart DBGI review for that line only and mark it **`Edited-review restarted`**, showing what changed and when. Already processed lines remain unchanged.
- A company may add a new product line to an existing reorder after other lines have been processed only when that product is covered by a discount awarded to that company. The new line receives its own DBGI verification; already processed lines remain unchanged. If the product's discount has expired, the company can add the line but must see a warning that the discount is expired. The old discount cannot be renewed after expiry; it must be awarded again.
- For an expired-discount line, the company must choose before proceeding either to submit it at the regular price or to wait for a new discount award. The old discount must not be applied. If the company chooses the regular price and DBGI verifies the line, that price becomes final; a discount awarded later does not apply retroactively. If the company chooses to wait, the line remains a company-only draft and is not submitted to DBGI. When DBGI awards a new discount for the product, notify the company that the draft can now be submitted. The draft remains available without automatic removal until the company submits or deletes it. If deleted, retain the deletion in audit history.

## 9. Discount renewal

- A company user may request renewal while an approved discount is active, supplying a **valid reason for DBGI review**. The request does **not** extend expiry or automatically preserve the discount. Admin can approve or deny with recorded reason and company notice. There is no fixed lifetime or maximum number of renewals if DBGI keeps approving justified requests.
- **Each approved renewal adds 30 calendar days.** If approved **before** the current expiry, add 30 days to the **existing expiry**, preserving remaining time. If approved **after** expiry, the discount is inactive throughout the gap and starts a **new 30-day period on the approval date**; gap orders receive no discount through the renewal action. A separately reviewed genuine pre-expiry purchase entered late follows Section 8 instead.
- Warn company users to **allow at least one working day for approval review** before expiry. This is a planning notice, not a guarantee of approval within one day. Show current expiry clearly and provide configured reminders. Create both a durable DBGI review-queue entry **and an admin notification** on every renewal request; highlight nearing-expiry requests so they are not missed. Failed email does not remove the portal task.
- Track requester, request time/reason, previous/new expiry, approver, decision time, any expressly revised terms and notification delivery. Actual initial validity duration, reminder lead time, Philippine business-day/calendar/time-zone behavior and exact clock cutoff still need selection. The **30-day renewal increment and before/after-expiry behaviors are fixed decisions**, not merely configurable guesses.

## 10. Edits, disputes and notifications

- A company user can edit its company's project registration; preserve original eligibility snapshot and full version/audit history. DBGI admin list shows a colored `Edited` pill by the title and `Review required` for material agency, scope, product, quantity, evidence or notice changes; DBGI reviews before they affect match, rank or approved pricing. Editing cannot convert a vague original claim into earlier priority.
- Companies may request review of their own rejection, match, rank, discount, renewal, reorder exception or withdrawal decision, with reason. DBGI records decision; a pending dispute does not silently suspend/change prior rank or pricing.
- **Per-event notification configuration already exists as a design decision**: DBGI configures portal-only versus portal plus email alerts according to event, while durable portal decision notices remain authoritative. No need for a new decision on verified reorder notifications; use this established configuration. Track recipients, delivery attempts/failures and admin follow-up; don't include sensitive evidence, competitor information or detailed pricing in emails.
- Provide role-specific dashboard/status cards, review queues and chronological project activity timeline. Admin queue includes evidence, matches, material edits, ranks/prices, withdrawals, disputes, expiring discounts, pending renewal requests, every reorder awaiting verification, exception clarification and overdue responses. Company dashboard shows its own approval/expiry, pending/provisional/verified reorders and decisions.

## 11. Data, audit, reporting and security

- Product/pricing history, company-scoped registrations and immutable original times, audit versions, approved discount versions, reorder claims and verified snapshots, correction/reversal records and notification events need relational links. Audit who changed what/when/why, including admin settings, schedule changes, rank decisions and exports.
- Authorized reports and exports may cover project pipeline/status, advance expiry, matching/ranking, approved discounts by company/item, expiring approvals and renewals, reorder volume/status/exceptions/corrections, audit activity and delivery failures. Restrict company exports to its own authorized data and only its own approved prices; full rankings remain DBGI-only.
- Server enforces role/company authorization, verification locks, eligibility, date and price-version selection, explicit admin changes, and monetary calculations. Secure attachments privately with authorized access, type/size controls and retention policies. Do not rely on browser `localStorage`, hidden inputs, or frontend filters as security controls.

## 12. Remaining decisions before final handoff

1. Final advance/published and category-specific field matrix, procurement lot representation and exact project statuses/transition table. The initial company-user fields, required competitor-item fields, searchable catalog-picker pattern and requested unit-price/justification capability are decided in Section 4.
2. Initial approved-discount duration and reminder settings; Philippine time zone/cutoff and working-day/holiday definition for the one-working-day planning notice. Renewal increment itself is 30 calendar days.
3. VAT calculation/display treatment for VAT-inclusive versus VAT-exclusive products, PHP rounding mode, multi-line total reconciliation, price variants and any additional tax/quotation needs. Have DBGI's finance/pricing owner verify tax treatment before production; do not infer it from an unrelated receipt project.
4. Exact timing for price selection when order date needs verification, effective-time changes within a day, late records and any disputed date evidence. The policy is to use the price effective on the **verified order date**, with DBGI review for a late/disputed user-supplied date.
5. Reorder verification checklist, reasonable anti-duplicate measures, clarification default deadline and minimum evidence for flagged exceptions. Ordinary order proof is **not mandatory**.
6. Held separately by user: detailed postponed/failed/cancelled/reposted government notice policy. The confirmed discount carryover to covered later purchases does not settle how all such notices affect registration/rank.
7. Final pages, permissions matrix, data schema, notification recipient selection/provider, retention/backup/attachment rules, hosting/deployment at `registration.dbgi.ph`, ranking tie/concurrency rule and acceptance tests. Prepare a separate technical/infrastructure proposal before implementation.

## 13. Acceptance checks

- Two employees from one company submit the same specific procurement: one company queue position, independent employee audit entries. A vague initial claim cannot backdate priority by later edits.
- A company sees only its own confirmed rank, approved products and applicable price calculations; direct API/export attempts cannot expose the full DBGI ranking or other companies' prices.
- Admin schedules a future price and later records an immediate price update: dated versions identify the applicable price, preserve scheduled history and never change already verified reorder snapshots.
- A VAT-inclusive default product can be set VAT-exclusive by admin; new calculations identify the basis, while old verified snapshots remain intact.
- A valid, matching reorder shows a **provisional** calculation immediately; DBGI verification is required to finalize it. Once verified, the record locks. A company can edit/withdraw a pending reorder with history/reason but can only request correction of a verified one.
- DBGI verifies a reorder on a documented date and snapshots the price version effective on that verified date. If the order is entered late or date disputed, a company-entered older date cannot unilaterally choose an older price or revive an expired discount.
- A company uses the same approved discount for multiple same-end-user/same-product reorders without a cumulative cap while active; fulfillment remains subject to availability. A new procurement notice may have its own ranking without automatically canceling covered existing pricing.
- A mismatch or late reorder is flagged, admin alerted, company given a clarification opportunity, and any missed deadline goes to overdue DBGI review rather than auto-rejection.
- A possible duplicate reorder is flagged and shown for company/DBGI review; DBGI can mark a confirmed duplicate `Duplicate-closed`, link it to the original and exclude it from separate counts without losing audit history.
- A reorder can contain multiple product lines. Matching lines can be processed while an unmatched line waits or is rejected independently. A pending line can be withdrawn, and edits restart review for that line with `Edited-review restarted`.
- An expired-discount line warns the company; it can be submitted at regular price or kept as a company-only draft while awaiting a new award. A later award does not change a line already verified at regular price. Deleted drafts remain in audit history.
- A discount request alone does not extend validity. Admin approval before expiry adds 30 days to existing expiry; after expiry starts 30 days on approval and does not cover gap purchases by renewal alone.
- Percentage line totals are calculated from full precision, rounded to two decimals at the line total. No automatic stacking with another discount; intentionally combined terms require explicit admin decision.
- DBGI admin documents correction or reversal after verification, preserving original snapshot and notifying company under configured channels. Admin identity and reason are recorded.
- A verified line cannot be directly changed. A reduction or cancellation request puts it on hold for DBGI review and preserves the original snapshot. If rejected, it returns to active with the reason shown.
- If a verified line has partially shipped, the company can submit one case covering both cancellation of the unshipped quantity and return of the shipped quantity. DBGI reviews and records separate outcomes for the two portions; approving one does not automatically approve the other. The original verified record remains unchanged.
- Two companies register purchases with the same normalized end-user name and address and complete SKU overlap. If exactly one existing scope qualifies and no conflict exists, the system links the later registration automatically and records its explanation. If multiple scopes qualify or any evidence conflicts, DBGI reviews the purchase description, evidence and lot scope. Companies confirmed in the same scope are ranked by their original eligible server-recorded submission timestamps.
